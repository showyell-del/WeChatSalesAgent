# Feature Landscape

**Project:** 微信客户成交 Agent  
**Domain:** 面向本地商家的微信私聊成交线索桌面 Agent  
**Researched:** 2026-07-23  
**Overall confidence:** HIGH（项目范围来自已确认需求；DeepSeek 行为来自官方文档；原生文件/视频发送仍受 Spike 结论约束）

## 产品功能结论

首版应是一条窄而完整的成交激活流水线：**连接一个已验证微信业务账号 → 本地筛选真人私聊 → 确定性提取信息 → DeepSeek 对必要证据做结构化判断 → 在桌面客户表中逐条审阅 → 导出 Excel 或人工确认后串行触达**。

功能中心必须是表格型线索工作台，而不是聊天浏览器、通用 CRM 或 Chatlog 管理后台。每个评分、字段和待发送文案都必须能回到真实聊天证据；任何数据读取、AI 分析或原生发送步骤失败，都要保留明确失败状态，不能用旧数据、规则分、自由文本或另一种发送方式冒充成功。

## 必需功能（Table Stakes）

缺少以下任一闭环环节，产品都不能称为可交付的“微信客户成交 Agent”。

| 功能 | 为什么必需 | 复杂度 | 完成边界 / 说明 |
|---|---|---:|---|
| 单账号连接与健康状态 | 所有线索、证据和发送目标必须归属于唯一业务账号 | 高 | 自动发现账号；逐库取钥验证；显示微信版本、数据新鲜度、当前账号和失败步骤；一个分析/发送任务只绑定一个账号 |
| 精确版本与 dylib 哈希门禁 | 错 profile 可能导致取钥失败、崩溃或错发 | 中 | 仅允许一个已经实机验证的 WeChat profile；版本、build、完整 dylib SHA-256、arm64 slice SHA-256 全部匹配才开放原生能力，否则停止，不提供兼容分支 |
| 首次解密与增量同步 | 半年聊天筛选必须基于完整且最新的数据 | 高 | 首次任务显示逐阶段进度；后续仅同步增量；任一库失败则本次数据状态失败，不能沿用旧快照并标成最新 |
| 时间范围与真人私聊范围选择 | 把约 1000 个历史联系人缩到有业务意义的候选池 | 中 | 用户选择起止时间；确定性排除群聊、公众号、系统/服务通知、机器人和无有效互动会话；显示纳入与排除数量 |
| 本地确定性候选预筛 | 控制隐私暴露、Token 成本和 AI 噪声 | 高 | 本地检测问价、课程/产品、地址、体验、付款、时间约束、联系方式、异议和负面信号；只把候选客户必要证据送往 DeepSeek |
| 结构化信息提取 | 商家需要可直接跟进的客户字段，而不是聊天摘要 | 高 | 确定性提取手机、座机、微信号、年龄/年级、区域、可用时间、预算、明确需求、阻碍；每个非空字段绑定消息 ID、时间和证据摘录；不确定则留空，不猜测 |
| DeepSeek 结构化意向分析 | 将分散证据转成一致的优先级和动作建议 | 高 | 用户配置 API Key、Base URL、模型；首版使用 `deepseek-v4-flash` 非思考模式；严格 JSON schema 输出 0–100 成交意向分、四档分类、证据引用、阻碍、建议动作和文案；空内容、截断、缺字段、枚举越界或证据不匹配均判失败 |
| 业务事实与禁用承诺配置 | 防止 AI 编造价格、优惠、库存或服务承诺 | 中 | 店铺产品/课程、价格、优惠、地址、营业时间、可承诺事项和禁用承诺是唯一业务事实源；配置缺失时相关文案不得补造 |
| 分析任务状态与失败明细 | 批量分析必须可审计，不能让局部失败消失在总结果里 | 中 | 每个客户记录 `pending/running/succeeded/failed`；失败显示 API/解析/schema/证据校验原因；成功和失败数量分开展示；失败结果不进入可发送集合 |
| 表格型线索工作台 | 本地商家最终需要一张可排序、可执行的客户表 | 高 | 固定核心列：客户、意向档、意向分、需求、联系方式、预算、可用时间、区域、阻碍、最近联系、建议动作、分析状态、发送状态；支持多条件筛选、排序、勾选和清晰空状态 |
| 证据详情面板 | 评分可信度来自可追溯证据，而不是模型措辞 | 中 | 从客户表打开侧边详情；按时间展示必要上下文、证据对应字段/结论、发送文案；禁止展示裸表名、SQL、Hook 偏移或通用聊天浏览器 |
| 聚焦业务动作的仪表盘 | 让老板快速知道“有多少人值得跟、先跟谁” | 中 | 仅显示客户总量、高意向、待激活、近期新增、意向分布、分析成功/失败、已选待触达、发送成功/失败；所有卡片可回到同一客户表过滤结果 |
| Token 与费用透明度 | AI 成本必须可预期、可核对 | 中 | 分析前展示候选人数和预计输入/输出 Token、预计费用；响应后记录实际输入、输出、缓存命中、缓存未命中 Token 和实际费用；展示本次及本地累计费用；价格来自显式模型配置并标明计价时间 |
| Excel 客户激活表导出 | 表格是商家复核、分工和线下跟进的通用交付物 | 中 | 导出 `.xlsx`，首行冻结、自动筛选、合理列宽、日期/分数/费用使用真实类型；包含当前筛选范围、证据摘录、建议动作、文案和发送结果；导出失败必须明确失败，不能改导 CSV |
| 个性化文案编辑与逐客预览 | 人工确认是避免错发和虚构承诺的核心门禁 | 高 | 公共要求只作为生成约束；每位客户生成独立且可编辑的最终文本；预览显示目标、最终文本、附件、人数、预计生成成本；修改后保存最终快照 |
| 附件选择与能力可用性 | 图片、视频和文件是本地商家常见触达素材 | 高 | 拖入后显示文件名、类型、大小、目标人数；只有已经通过真实接收、Ack、取消和清理验收的适配器才显示为可发送；不能把文件/视频伪装成图片或互相替代 |
| 人工确认后的串行发送队列 | 共享 native 状态不能并发，且必须防止错发 | 极高 | 一次最终确认后，由唯一 native session owner 串行执行；逐客户显示 `queued/running/succeeded/failed`、Ack 和 cleanup；任务级禁止并发启动第二会话 |
| 取消与失败处置 | 用户必须能停止未发送目标，并知道哪些客户未触达 | 高 | 可在发送前取消单客；执行中只取消尚未进入不可逆原生步骤的命令；未知 Ack 不得标成功或自动重发；失败后由用户审阅并显式决定是否重新建任务 |
| 任务终态与微信健康检查 | “消息发出”不是完整成功，残留 helper 会破坏微信稳定性 | 高 | 结束/取消后完成脚本卸载、会话断开、Frida 关闭、当前任务 helper 定向清理和微信健康检查；清理不完整时任务不得显示完整成功 |

## 差异化功能（Differentiators）

这些能力建立产品可信度，应在核心闭环稳定后加入；其中前四项尤其值得保留，因为它们直接强化“可审计、低成本、不乱发”。

| 功能 | 价值主张 | 复杂度 | 依赖 / 建议 |
|---|---|---:|---|
| 字段级证据链与一键回看 | 竞品式摘要只能“看起来合理”；字段级引用让老板能在数秒内核对电话号码、预算、阻碍和评分原因 | 中 | 依赖稳定消息 ID、证据摘录与详情面板；首版纳入 |
| 本地规则 + 必要证据的两阶段分析 | 显著减少上传聊天量、无关客户分析和 Token 支出 | 高 | 依赖本地筛选词典/规则、候选统计和脱敏边界；首版纳入 |
| 成本账本与缓存可见性 | 用户可以核对每次任务实际成本，而不是只看到估算 | 中 | 读取 API `usage` 中输入/输出及缓存命中/未命中 Token；稳定系统前缀置于请求最前部以提高缓存机会，但不得承诺命中率；首版纳入 |
| 事实约束文案校验 | 在发送前拦截未配置的价格、优惠、库存和承诺，降低商业风险 | 高 | 依赖业务配置、原始证据、结构化文案字段和发送前校验器；首版纳入 |
| 仪表盘到客户表的可解释下钻 | 每个数字都能打开对应客户集合，避免“漂亮但不可行动”的大盘 | 中 | 依赖统一筛选状态与指标口径；首版纳入 |
| 可复现分析任务快照 | 保存账号、时间范围、业务配置版本、模型、提示版本、证据和结果，使导出/复核口径一致 | 中 | 不保存半年完整上传包；依赖任务模型和本地存储；建议首版纳入 |
| 触达结果回写同一工作台 | 筛选、发送和结果不分散到多个页面，老板能继续处理未发送/失败客户 | 中 | 依赖发送状态机与客户表；首版纳入 |
| 人工标注“有效线索 / 已成交 / 未成交” | 为后续用真实业务标签校准意向分提供数据基础 | 中 | 首版可只做本地标签记录；在样本量和校准方法成立前，禁止把意向分改称成交概率 |
| 分析质量抽检视图 | 按意向档抽样核对联系方式和证据，形成上线验收闭环 | 中 | 依赖字段级证据和本地人工标注；建议作为真实业务验收工具，不做常驻复杂导航 |

## 明确反功能（Anti-Features）

以下内容应从设计、导航和路线图中排除，而不是隐藏或加兼容开关。

| 反功能 | 为什么避免 | 直接做法 |
|---|---|---|
| Web UI / 本地 Web 控制台 | 偏离专业 macOS 桌面产品和本地数据边界，还会复制 Chatlog 通用后台 | 只实现原生桌面面板；不保留 HTTP 调试页面作为用户功能 |
| Chatlog 通用后台复刻 | 裸数据库、SQL、通用搜索、媒体浏览和技术参数不产生首版成交价值 | 仅抽取账号、同步、历史读取、仪表盘概念和 native sender 核心 |
| 群聊分析、群成员排行、群聊对比 | 群聊关系与私聊成交目标不同，会扩大数据与产品范围 | 查询入口即限定真人一对一私聊 |
| 通用 CRM 销售管线 | 阶段自定义、工单、团队权限和全渠道客户管理会淹没核心工作台 | 只保留本次线索筛选、人工标签、触达状态和 Excel 交付 |
| 朋友圈、收藏、通用 RAG、知识图谱 | 首版没有直接、可验证的成交收益 | 不建入口、不建索引、不预留抽象层 |
| 上传半年完整聊天给模型 | 成本高、隐私暴露大、噪声多 | 本地预筛后只发送候选客户的必要证据片段 |
| AI 自由文本结果或本地规则兜底分 | 自由文本不可稳定入表；兜底分会冒充模型成功 | 只接受通过 schema 和证据校验的 JSON；否则该客户失败 |
| AI 猜测空字段 | 会制造虚假电话、预算、需求和承诺 | 不确定字段保持空值并显示“未从聊天提取” |
| 未经校准的“成交概率”或预测收入 | 没有真实成交标签时不具统计含义 | 只称“成交意向分”；仪表盘不展示虚构预测 GMV |
| 未预览自动群发 | 容易错发、骚扰和虚构承诺 | 必须逐客户预览并进行一次明确最终确认 |
| 自动重发未知 Ack | 可能造成重复消息 | Ack 不明确即失败；用户核对后显式创建新任务 |
| 并发 native 发送 | 会竞争共享微信/Frida 状态，增加错发和脏清理风险 | 全局唯一 session owner 串行执行所有类型 |
| 未验证的附件类型占位按钮 | “暂不可用”入口会误导用户认为功能已交付 | 适配器通过实机完整验收后才出现；未验证类型从 UI 移除 |
| 文件/视频类型伪装复用 | 接收端语义、上传链路和协议不同；已验证简单文件路径失败 | 文件与视频各自独立原生适配器和验收 |
| Hermes、系统分享、剪贴板、键鼠模拟 | 无法满足可识别 Ack、稳定清理和原生确定性 | 发送适配器失败就失败，不切换路径 |
| 多微信版本兼容层 | 原生偏移与对象布局随版本变化，兼容猜测会导致崩溃或错发 | 首版只维护一个实机验证 profile，其他版本直接拒绝 |
| Windows / Intel Mac 分支 | 未验证且会扩大原生测试矩阵 | 首版只编译和验收 macOS Apple Silicon |
| 技术调试参数暴露给商家 | 偏移、Hook 日志、SQL 和 helper 进程不是业务决策信息 | 用户界面只展示阶段、对象和可行动失败原因；诊断留在受控日志 |

## 功能依赖

```text
单一已验证 WeChat profile
  → 账号发现与逐库取钥验证
  → 首次解密 / 增量同步
  → 单账号私聊数据集
  → 本地范围过滤与确定性提取
  → 候选客户 + 字段级证据
  → DeepSeek 严格 JSON 分析
  → 证据/schema/业务事实校验
  → 表格工作台 + 证据详情 + 仪表盘 + Excel
  → 逐客文案编辑 / 附件预览 / 最终确认
  → 唯一 native session owner 串行队列
  → Ack + cleanup + 微信健康检查
  → 触达结果回写工作台与 Excel
```

关键的横向依赖：

- **业务配置**同时约束 DeepSeek 提示、文案事实校验和最终预览。
- **统一任务快照**同时支撑成本账本、结果复核、Excel 导出和问题定位。
- **稳定消息标识与证据引用**同时支撑提取字段、AI 评分、详情面板和人工抽检。
- **发送适配器能力注册表**只注册通过实机验收的类型，直接决定附件区可见能力。
- **单一发送状态机**是取消、Ack、清理、工作台回写和 100 目标连续测试的共同基础。

## 建议的桌面信息架构

保持三个业务面板即可，避免多余导航：

1. **连接与分析**：账号/版本健康状态、时间范围、业务配置摘要、候选数量、预计成本、分析进度与明确失败。
2. **客户工作台**：顶部紧凑仪表盘；下方主客户表；右侧证据与编辑详情；Excel 导出从当前筛选结果触发。
3. **触达确认与状态**：已选客户、逐客最终文案、附件摘要、目标人数、最终确认、串行队列和清理终态。

不单独建立聊天浏览、模型实验、发送调试或数据库管理页面。

## MVP 优先级与路线图建议

### 第一阶段：可信数据集

优先完成单 profile 门禁、账号发现、取钥、逐库验证、解密、增量同步、单账号绑定和真人私聊过滤。没有这层，后续所有表格与评分都可能建立在错误账号或旧数据上。

### 第二阶段：证据型线索表

完成确定性提取、字段级证据、客户表、详情面板、筛选排序和 `.xlsx` 导出。先让真实商家在不依赖 AI 的情况下核对候选池和联系方式质量。

### 第三阶段：DeepSeek 分析与成本账本

接入业务配置、必要证据压缩、严格 JSON、证据/schema 校验、成交意向分、建议动作、个性化文案以及预计/实际费用。任何客户失败都保持失败，不产生替代分数或文案。

### 第四阶段：桌面业务闭环

补齐紧凑仪表盘、下钻、任务快照、逐客编辑和最终预览。此阶段完成“筛选结果可审计、可导出、可确认”，但在发送适配器未全部验收前不展示对应按钮。

### 第五阶段：原生受控触达

文本、图片、视频、文件各自完成真实接收、可识别 Ack、取消与清理测试后，再统一接入单 session 串行队列。最后进行真实半年私聊全链路与至少 100 目标连续发送验收。

**建议延期：** 真实成交标签校准、预测价值指标和团队 CRM 能力。前者需积累标签后专项验证；后两者在首版会制造无依据数字或扩大范围。

## 必须在规划前解决的范围冲突

| 冲突 | 证据 | 建议 |
|---|---|---|
| WeChat 首版版本不一致 | `REQUIREMENTS.md` 写 `4.1.11.54`；`PROJECT.md`、`Agent.md` 与 Spike 001 的实机 profile/哈希均指向 `4.1.11.55` build `269111` | 选定一个唯一 source of truth。基于现有验证证据，应将首版统一为 4.1.11.55；在文档统一前不要规划“双版本支持” |
| 文件发送路径尚未成立 | Spike 001 已否定简单 `uploadappattach -> sendappmsg`；文件消息未达到 Req2Buf/Buf2Resp | 文件适配器保持研究门禁，不允许因需求已写入而提前出现在产品 UI |
| 视频与串行生命周期未验证 | Spike 002、003 仍为 PENDING | 作为高风险独立阶段，必须先 Spike 成功，再进入产品集成 |

## 功能级验收原则

- **数据真实性：** 客户、字段、分数、费用和发送结果都必须能追溯到明确来源。
- **状态真实性：** 失败就是失败；不把缓存旧值、规则结果、自由文本、调用成功或未知 Ack 显示成业务成功。
- **界面真实性：** 只有实际完成并通过实机验收的发送类型才可见。
- **隐私最小化：** 原始聊天默认本机处理，外发载荷只包含完成当前候选分析所需片段。
- **范围克制：** 桌面端只呈现连接、分析、客户表、证据、成本、导出和受控发送。
- **商业可行动：** 仪表盘任何指标必须能下钻到客户集合；客户表任何 AI 结论必须能回看证据。
